# 配置基础

[配置指南](README.md) · 下一篇：[首次设置](first-setup.md)

## 设置存放在哪里

配置 AskFlow 有三个不同的地方：

| 位置 | 示例 | 更改如何生效 |
| --- | --- | --- |
| 后端环境或 `.env` 文件 | 数据库、模型连接、启用功能、限制 | 重启后端 |
| Web 构建环境 | `VITE_ASKFLOW_FEATURES` | 重启 Web 开发服务器，或重新构建并重新部署 Web 应用 |
| 已存储的应用设置 | 意图映射、提示词版本、团队、连接器记录 | 通过相关页面或经授权的集成保存；验证受影响的工作流 |

更改 `.env` 不会更改已存储在数据库中的连接器记录。编辑 Web 环境不会配置后端。本指南会为每项任务指明正确的位置。

## 什么是环境变量？

它是提供给正在运行的程序的一个命名值。例如：

```dotenv
HANDOFF_TIMEOUT_SECONDS=300
```

名称是 `HANDOFF_TIMEOUT_SECONDS`；值是 `300`。这告诉 AskFlow 对无人认领的人工支持请求使用五分钟的等待阈值。

**默认值（default）** 是未提供值时使用的值。你不需要把每个设置都复制到配置文件中。从你的安装所需的少数几个值开始，其余的保持默认值即可。

## 使用正确的文件和工作文件夹

对于本指南中的本地命令，请使用 `apps/api/.env`，并**从 `apps/api`** 启动 API。程序在其工作文件夹中查找 `.env`，不会自动在每个源文件旁边查找。相对的数据库和存储路径也取决于该文件夹。

Web 应用在 `apps/web` 中使用自己的 Vite 环境文件，例如 `apps/web/.env.local`。把 `VITE_ASKFLOW_FEATURES` 放入 API 文件并不会配置 Web 应用。

托管服务可能通过它自己的设置面板而不是文件来提供环境变量。容器和服务管理器设置必须应用到实际的 API 进程；重新启动容器而不重新创建其环境，可能会保留旧值。

## 编辑 dotenv 文件

使用纯文本编辑器。文件名恰好是 `.env`，包括开头的点，没有额外的 `.txt` 扩展名。

```dotenv
# 以 # 开头的行是注释。
ASKFLOW_ENV=development
ASKFLOW_PROFILE=full
SERVICE_TASKS_ENABLED=true
SERVICE_TASK_POLL_SECONDS=5
```

- 每行放一个设置，并使用本指南中所示的拼写。
- 开/关开关使用 `true` 或 `false`。
- 使用普通数字，不带单位或千位分隔符：`300`，而不是 `5 minutes`。
- 对包含空格或特殊字符的文本加引号。
- 每个设置只保留一行有效的。
- 删除或注释掉可选设置以恢复其默认值。空值并不总是等同于省略该值。

有些值有特定的格式：

```dotenv
CORS_ORIGINS='["https://support.example.com","https://portal.example.com"]'
ASKFLOW_FEATURES=+teams,+notify,-mcp
SERVICE_TASKS_GOALS=order_status,ticket_resolution
```

`CORS_ORIGINS` 需要 JSON 数组：方括号，条目用双引号。裸的逗号分隔来源字符串当前会导致环境解析失败。功能更改和任务目标则使用逗号分隔的文本。

`example.com` 地址以及诸如 `REPLACE_WITH_PROVIDER_KEY` 的值是占位符，不是可用的服务或凭据。在启用相关连接之前请替换它们。

## 理解哪个值优先

对于正常的应用启动，shell 或托管服务提供给进程的值会覆盖 `.env` 中的值；`.env` 中的值会覆盖默认值。

例如，如果你之前运行了 `export ASKFLOW_PROFILE=mvp`，那么把文件编辑为 `ASKFLOW_PROFILE=full` 不会覆盖那个已导出的值。在本地 shell 中，用以下命令移除这个特定的覆盖：

```bash
unset ASKFLOW_PROFILE
```

然后从预期的文件夹重启 API。在诊断问题时不要打印或分享整个环境：它可能包含凭据。只检查你正在调查的那个特定的非机密值。

`.env` 中未知的设置会被忽略，因此拼错的名称可能看起来生效了，实际却没有效果。请查看 [参考](reference.md)，而不要猜测名称。

## 更改后重启

对于本地开发设置：

1. 保存你的 `.env` 更改。
2. 在运行 API 的终端中，按 **Ctrl+C** 并等待它停止。
3. 从 `apps/api` 出发，在其虚拟环境已激活的情况下，再次运行相同的 API 启动命令。
4. 打开 `/health`，并测试你更改的功能。

不要依赖 `--reload` 来检测 `.env` 的更改。许多客户端和设置在进程的生命周期内会被缓存。

对于共享安装，请让其运维人员通过部署系统重启所有受影响的 API 进程。Web 环境更改需要单独的 Web 重启或重新构建。控制新请求的设置可能不会改变已受理的工作；请参见 [服务运营](service.md)。

## 保留一条退路

在更改现有安装之前，请将先前的配置保存在私有位置，并记录你更改了什么。包含机密的配置副本需要与原文件相同的访问限制。将它排除在共享文档和源代码控制之外。

要撤销一个简单的限制或功能更改，请恢复先前的值并重启。数据库迁移、文档重建索引、密钥更改和外部业务操作会有额外的后果：恢复环境文件并不能撤销这些更改。

API 密钥或令牌是一种凭据，就像服务的密码一样。只能将它存储在后端的私有配置或主机的机密管理设施中。绝不要把它放在 `VITE_` 变量中：Web 构建值可能会暴露给浏览器。
