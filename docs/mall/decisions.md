## 风险及处置

| 风险 | 设计措施 | 验证/边界 |
|---|---|---|
| 用户通过旧登录绕过商城MFA/吊销 | 共享密码/安全入口和JWT/WS校验 | 旧接口、OIDC、WS越权矩阵必须新增；不修改旧profile无安全记录用户行为 |
| SQLite StaticPool 单连接并发“看似通过” | 业务测试内存fixture；并发另用文件SQLite多连接 | 不拿单连接 asyncio.gather 证明数据库竞争 |
| 退款/支付外部超时未知 | 意图先提交、永久业务key、查询补偿 | mock可验证，真实支付连接器未实现前不宣称真实生产退款 |
| 钱包链分叉/账户死锁 | 独立currency链头、稳定锁顺序、CAS | 200并发、篡改、DB故障/事务回滚测试 |
| Redis故障导致多实例进程锁 | staging/production拒绝不安全组合 | 不自动切memory；演练显式PG/DB降级部署 |
| 配置事件只送一个实例 | 广播失效+版本读取+短TTL | 多实例热更新测试；不热改Harness常量 |
| webhook重复/金额篡改/乱序 | HMAC、时间窗、唯一流水、server比对、单次记账 | 100回调、伪造和late_payment测试 |
| 设备/IP关联误伤真实家庭/公司 | 仅风险信号、阈值、人工review | NAT共享和支付账户关联测试，规则可审计回滚 |
| 压测目标与当前硬件不符 | 保存规格/配置/数据/报告，首次校准 | 全部指标当前未测；不得填造QPS/P99 |
| 新迁移错误影响原客服 | 冻结schema/双向双方言、独立bootstrap | 空库/既有create_all库/旧migration库三矩阵 |
| 无运行验证导致静态编写风险 | 分阶段小变更、完整待运行清单、诚实STATUS | 本轮不能提供通过率/覆盖率/可部署验收证据 |

# 实施补充（用户已指示继续）

旧认证入口在商城档启用时复用商城登录服务，旧注册入口提示使用验证注册；
OIDC 仍复用原有 subject 绑定及角色同步，再执行商城 MFA 检查。
会话安全检查同时覆盖 HTTP 和每个 WebSocket 回合。关闭商城时保留原有流程。
验证码通过加密数据库待发送任务异步投递，outbox 和日志不保存明文验证码。
注销采用保留引用、脱敏内容、吊销会话方式，先检查未完成订单和钱包余额。
财务记录只追加；账户快照、分录和链头在同一数据库事务更新。

## 事务实现补充

商城 HTTP 写请求在 SQLite 中先 BEGIN IMMEDIATE，再认证/读业务状态；PG 锁定客户行。
跨客户库存竞争仍必须使用 available>=qty 条件 UPDATE。后台任务采用独立事务，
同样锁定业务聚合；不能使用进程锁代替数据库约束。
外部支付请求/退款按持久业务键提交；mock 的网关流水与平台支付记录分开存储，
迟到回调进入退款清算而不复活已取消订单。前端金额只能请求钱包抵扣上限，最终金额重算。
财务记账锁定币种链头后，再按账户 code 排序锁账户；幂等重放必须比较全部分录摘要。
冻结采用独立用户 frozen 科目，保证可用余额和冻结余额都可从分录独立重建。

# 续作：事务、支付与验证边界

- 验证码发送复用 `login_attempts` 的独立 verification scope，通过唯一键和条件更新保留发送窗口，避免并发读后写绕过频控。
- 客服驱动的业务写入放在 savepoint 中；失败回滚业务写入，再记录不包含个人信息的拒绝审计。认证等级缺失按 L1 处理。
- 支付退款端口接收不可变 DTO、返回支付侧收据，禁止修改订单领域 ORM 对象。mock 网关操作与业务事务同库提交；未来网络网关必须提供持久化 intent、查单补偿和未知结果状态，不能直接替换成 HTTP 调用。
- 支付和网关对账按 UTC 业务日进行，覆盖金额、币种、终态、遗漏账单和重复引用。对账只记录差异，不自动改写证据。
- 独立 worker 每个业务对象一个事务和租约，避免同批跨订单持锁；失败对象不阻塞整批。数据库条件更新仍是最后防线。
- 上述为实现决策，当前禁止运行的约束不变；不代表代码或性能已经验证。

## 本轮收敛（feat/mall-platform-completion）

- 用户已明确授权接续草稿和提交，仍禁止运行验证。
- 空库 PostgreSQL 在治理迁移创建 `channel_identities` 时已经需要 `users`。
  增加最早的冻结客服基线迁移，并将原首个迁移的前驱接到它；保留原修订 ID。
  基线不创建后续迁移拥有的表，不预建 `oidc_subject`；已迁移部署不会重跑前驱。
  已有 create_all 但未登记版本的数据库仍需人工核对后登记，禁止自动 stamp。
- 每日对账复用数据库租约和 reconciliation_runs；以 UTC 昨日为业务日，成功结果可重复查询，
  失败回滚后重试。差异处置保留原 expected/actual，只追加审计和处置引用；
  资金冲正沿双人调账审批，不能通过“关闭差异”直接更改余额。
- 商城限流启用时避免旧单 IP 中间件再次施加较低限额；关闭商城或商城限流时保持原限制。
  HTTP 日志中间件在商城档包住限流层，使拒绝响应也有 trace_id；旧档顺序不变。

- 商城 outbox 重试时间放入 `mall_event_retries` 扩展表，不改变既有 outbox 列含义。
  每个事件单独领取和提交；失败记录异常类型并指数退避，原 outbox attempts 仍决定死信。
- 搜索端口仅提供有界候选提示；候选超限时回退参数化数据库检索，避免游标页永久漏商品。
  FTS/ES 相关性排序和大数据量 search_after 优化仍需单独验收。
- 财务对账先创建并锁住币种链头，空账本也遵守一致性边界；当前按币种串行记账，
  达到钱包吞吐指标前必须压测此锁，不把正确性锁当作高吞吐证据。
