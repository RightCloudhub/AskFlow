# 客服助手与 Agent 定义的差异及严格化设计

状态：对照与收敛文档（差异清点 + 严格化设计），2026-10-03。
适用：AskFlow 客服助手（聊天入口 + `apps/api/app/services/agent/`）。
关系：[customer-service-agent.md](../prd/customer-service-agent.md) 给出目标定义与完整设计；本文回答三个问题：现状与定义的**逐条差异**是什么、如何**收敛**到严格符合、如何**验收**。重构执行计划（阶段切片与 PR 划分）见 [agent-refactoring-plan.md](./agent-refactoring-plan.md)；实现记录见 [customer-service-runtime.md](./customer-service-runtime.md)、[customer-preference-memory.md](./customer-preference-memory.md)、[customer-service-lifecycle.md](./customer-service-lifecycle.md)。

一句话结论：现状是「一条完整 Agent 路径（仅订单查询）+ 一条传统消息管线（其余全部业务）」。严格化 = 把订单路径的运行时推广为所有业务目标的统一运行时，并按本文 §5 补齐判断、环境与记忆三块。

## 1. 判定标准

严格 Agent 定义（与 PRD §1 一致）要求七项能力**同时**成立，且每项都有可检验的证据：

| # | 能力 | 判定证据（必须可检验） |
|---|------|------------------------|
| 1 | 目标持有 | 目标跨轮次、跨进程存在，直到完成或明确终止 |
| 2 | 环境感知 | 动作依据来自环境事实（含来源与新鲜度），而非仅本轮文本 |
| 3 | 自主判断 | 候选动作被提出、比较、选择，选择理由被记录 |
| 4 | 动作执行 | 动作是隔离单元：有契约、有超时、可幂等重试、可补偿 |
| 5 | 反馈校正 | 结果被分类（瞬时/权限/永久/冲突），触发重试、换路、询问或转人工 |
| 6 | 记忆 | 任务、客户事实与经验跨轮次保留，可检索、可过期、可删除 |
| 7 | 结果验证 | 完成条件由应用裁定，证据可追溯；未验证不算完成 |

明确不算证据的项：微步骤数量多、工具调用次数多、调用了 LLM、流程里写了循环。把固定流程包装成循环不构成自主判断；mock/模拟数据不构成完成证据；代码里存在接口不构成能力已上线。

## 2. 现状清点：两条并存路径

消息先经过 `ChatTurn`（`apps/api/app/services/chat/session/turn.py`）：命中订单查询时创建持久任务（路径 B）；其余消息进入旧消息管线（路径 A）。

| 维度 | 路径 A：消息管线（旧） | 路径 B：服务任务运行时（新） |
|------|----------------------|------------------------------|
| 入口 | 所有未命中订单查询的聊天消息 | 订单查询消息（先于 A 判定） |
| 代码 | `agent/pipeline/runner.py`、`pipeline/handlers/*`、`loop/engine.py` | `agent/service/*`、`chat/service_tasks.py`、`workers/service_tasks.py` |
| 业务范围 | rag / tool / ticket / handoff / clarify / refuse 六个固定路由 | 仅 `order.get_status` 一个目标 |
| 状态载体 | 会话消息、槽位、工单/转交记录 | 持久任务：检查点 + 操作账本 + 决策 + 证据 + 恢复信号 |
| 失败处理 | 固定重试或直接失败文案 | 错误分类 → 退避重试 / 换路 / 询问 / 转人工 / 对账 |
| 恢复 | 无（进程重启丢失本轮上下文） | 派发租约 + 检查点，重启后可继续 |

### 2.1 路径 A 与定义的差异

| 能力 | 路径 A 实际行为（代码证据） | 差异结论 |
|------|------------------------------|----------|
| 目标持有 | 每条消息独立分类、独立路由（`pipeline/runner.py`）；跨轮只保留有界历史与槽位，没有"目标"对象 | 不符合 |
| 环境感知 | 无环境快照；工具参数来自正则槽位与固定路由表；工具返回 `ok`/`mock` 都按成功处理（`loop/engine.py`） | 不符合 |
| 自主判断 | 路由查表；`LoopEngine.run` 以固定工具名与固定参数执行，`plan_hint` 被显式忽略（`loop/engine.py:43`） | 不符合 |
| 动作执行 | 工单/转交处理器只产生 `side_effects` 字典（`handlers/ticket.py`、`handlers/handoff.py`），事后由副作用处理器落库；无契约、无幂等键、无超时、无补偿 | 不符合 |
| 反馈校正 | 无错误分类；失败要么固定重试，要么直接返回失败文案 | 不符合 |
| 记忆 | 会话内历史 + 槽位；无跨会话记忆 | 部分（仅会话内） |
| 结果验证 | RAG 回答有引用与 grounding 验证（诚实 RAG）；工具与工单/转交动作无任何验证 | 部分 |

### 2.2 路径 B 与定义的差异

| 能力 | 已实现（代码证据） | 仍存在的差异 |
|------|--------------------|--------------|
| 目标持有 | 任务持久化 goal/inputs/completion_condition/status/ledger/version（`service/contracts.py`），跨进程恢复（`store.py` 版本 CAS） | 只有订单查询一个目标；其余业务消息不建任务 |
| 环境感知 | 每次 tick 重新 observe；`_fresh_view` 丢弃模拟与过期证据（`service/runtime.py`）；读取权限与偏好 | 环境事实只有订单归属等少量字段；无工具健康、队列时长、通道能力 |
| 自主判断 | propose → 硬约束过滤（`registry.py` 的 unknown_operation / unavailable / permission_denied / invalid_arguments / precondition_failed，加 already_attempted / reconcile_required / 冷却）→ 选 priority 最小 → `Decision` 记录 candidates/rejected/selected/reason | 策略只提出单候选，比较不成立；无计划依赖图；无重新规划触发器 |
| 动作执行 | `Operation` 契约（版本/权限/effect/schema/超时/重试/补偿字段）；Executor 先写账本再调用；幂等键复用返回既有回执；写操作超时 → unknown + reconcile（`executor.py`） | 注册表只有 `order.get_status`（read）；无写操作、无补偿执行、无跨任务对象锁 |
| 反馈校正 | `RecoverySignal` 分类与动作 retry/fallback/ask_customer/owner_review/reconcile（`recovery.py`）；读失败退避重试；非读失败不盲目重放 | 无费用预算与任务总时限（只有 max_calls 与单操作超时） |
| 记忆 | 任务检查点 + 偏好记忆（3 键、显式同意、版本化纠正、过期、墓碑删除） | 无客户事实、事件、经验记忆 |
| 结果验证 | 应用侧 verify（权限 + 归属 + 证据匹配，`order.py`、`chat_order.py`）；模拟证据不满足完成条件；未验证不 resolve、不外泄 | 证据只来自系统回执，无客户/人工确认通道 |

### 2.3 与既有文档口径的差异

`customer-service-runtime.md` 与 `STATUS.md` 的「尚未实现」清单以**通用/全业务范围**为准绳。其中「聊天入口绑定、后台定时扫描」在**订单查询范围**内已由提交 79dcdf4 落地（聊天入口建任务、派发 worker、结果回写）；清单其余条目（事件订阅、退款连接器、自由文本客户事实、经验检索、跨任务加锁、计划依赖图、费用与总时限预算）仍未实现。引用时需区分「订单路径」与「通用能力」，以本文 §2 的现状表为代码口径。

## 3. 按五条轴线的差异

用户强调的五条轴线逐条对照（每条给出「定义要求 → 现状 → 差异」）：

| 轴线 | 定义要求 | 现状 | 差异结论 |
|------|----------|------|----------|
| 业务步骤微步骤化 | 每个业务步骤拆到可独立执行/验证的微步骤 | 路径 B 已微步骤化（观察→判断→执行→验证→记录），但只覆盖订单查询一条业务；路径 A 的粒度是「处理器」 | 其余业务的微步骤目录（PRD §5）未落地 |
| 操作独立单元 | 每个操作有完整契约，可独立重试与补偿 | 契约结构完整，但注册表只有一个读操作；工单/转交仍是「意图标记 + 事后副作用」 | 写操作、补偿、对账未落地 |
| 自主判断 | 候选被提出、比较、选择并记录理由 | 决策记录结构存在，但每类目标只有单候选 | 比较不成立；无计划图与重新规划 |
| 环境最优 | 按环境事实过滤候选并按效用/优先级选择 | 有环境快照与硬约束过滤；偏好只影响文案 | 无多候选效用比较；偏好不参与动作选择 |
| 记忆 | 六层记忆可检索、可过期、可删除 | 任务记忆 + 偏好 3 键 | 事实、事件、经验记忆未实现 |

## 4. 差距清单（按优先级）

1. **通用入口缺失**：除订单查询外，业务消息仍走旧管线，不建任务、无目标持有（§5.1）。
2. **操作目录过窄**：写操作（退款、改地址、重发通知）与补偿、对账、跨任务对象锁未落地（§5.2）。
3. **判断未成比较**：单候选策略、无计划依赖图、无重新规划触发器（§5.3）。
4. **环境未最优**：环境字段不足（工具健康、队列时长、通道能力），无多候选效用比较（§5.4）。
5. **记忆不足**：客户事实、事件、经验三层未实现；记忆写/读管线只对偏好存在（§5.5）。
6. **验证通道单一**：无客户/人工确认作为完成证据的通道（§5.6）。
7. **预算不全**：无费用预算、任务总时限、无进展循环上限。

## 5. 严格化设计

### 5.1 统一入口：目标受理

入口层只做一件事：把消息判定为**目标候选**、**直接回答**或**澄清**，判定结果被记录（可审计）。

- 目标候选：包含业务动作意图、需要外部动作或多步才能完成 → 创建/续接任务。去重键 = 会话/客户 + 业务对象（沿用 `chat/service_tasks.py` 的 uuid5 规则）；任务创建与消息持久化同事务（`insert_once` 模式）。
- 直接回答：知识问答类消息仍由 RAG 直接回答（其目标=给出有证据的回答，验证=引用与 grounding），不建任务。
- 澄清：判定不确定时走现有 clarify 路由，不猜。
- 多目标消息：拆为主目标 + 后续目标，全部记录，后续目标在依赖满足后进入执行。
- 判定层只做分类，不授予权限：权限永远来自认证代码（`Environment.permissions`）。

验收：订单查询建任务（现状保持）；「我要退款」建退款目标任务；「你们几点上班」直接回答且不建任务。

### 5.2 微步骤与操作单元

每个业务步骤拆成微步骤序列，每个微步骤是六类单元之一：观察 / 判断 / 交互 / 执行 / 验证 / 记忆。拆分标准：单个单元只有一种效果，可被独立重试或补偿；纯计算不拆。

操作单元必须过注册表（`Operation` 契约），新增操作检查清单：

1. operation_id 与 version；effect（read/write/notify）与 permission；
2. input_schema / output_schema / precondition；
3. timeout 与 max_retries；幂等键推导规则；
4. 写操作必须声明补偿与对账方式，超时一律记 unknown，不盲目重放；
5. 通知与业务效果分离（notify 单独成操作）。

优先落地顺序：`ticket.create`（从副作用迁移）→ `handoff.enqueue` → `notify.send` → `order.modify_address` → `refund.submit`（连接器未就绪前保持 owner_review）。写操作上线前先落地**按业务对象跨任务加锁**（同一订单的并发写只允许一个任务持有）。

### 5.3 判断与决策记录

- 每类目标一个策略模块（现有 `order.py` 是模板）：observe / propose / verify 三个回调。
- propose 必须产出 ≥1 个候选（来源：规则、模型、经验，均可），带 priority 与理由；多候选时按效用或优先级选择；无可行候选 → `owner_review:no_feasible_action`（现状保持）。
- 决策记录在现有字段（candidates / rejected / selected / reason）上补 expected_result 与 stop_conditions。
- 计划依赖图：需要多个操作的目标（如退款 = 核验 → 提交 → 等结算 → 确认）用子目标依赖表达，依赖通过 precondition 与证据门控；无依赖的操作默认按风险串行（read < notify < write）。
- 重新规划触发器：环境事实变化、验证失败、预算消耗过半、连续无进展（新增 MAX_NO_PROGRESS_CYCLES）、策略回调失败。

### 5.4 环境最优选择

环境快照字段（PRD §7）逐字段落实「来源 + 新鲜度」：权限（认证）、可用操作（插件开关）、业务事实（连接器，带 observed_at/expires_at）、偏好（PreferenceStore）、工具健康、库存、队列时长、通道能力、时限与预算、授权范围。

选择顺序固定为三步：**硬约束过滤**（注册表 rejection）→ **候选去重与合并** → **效用或优先级选择**。效用函数只在估计值有来源时启用（不得编造概率）；无估计时用确定性排序：风险最小 → 成本最小 → 最快 → 最稳定。

偏好进入选择：language / response_detail 影响回复组织，contact_channel 影响通知操作的候选；偏好缺失或过期按默认并记录降级（`preference_status` 现状保持）。偏好与记忆永远不授予权限（`contracts.py` 既定原则）。

验收：工具健康 ok→degraded、库存有→无、队列短→长时，选择结果必须改变，且拒绝理由写入决策记录。

### 5.5 记忆

六层模型与现状映射：

| 层 | 载体 | 现状 |
|----|------|------|
| 工作记忆 | 轮内上下文与有界历史 | 已有（会话内） |
| 任务记忆 | Task 检查点（目标/账本/决策/证据） | 已有 |
| 客户事实与偏好 | 偏好 3 键 | 偏好已有；事实待建 |
| 事件记忆 | 任务流转、恢复信号、交付记录 | 部分存在，缺可查询时间线 |
| 业务知识 | RAG 语料 | 已有（只读检索） |
| 经验记忆 | 成功决策路径 | 未实现 |

统一记录字段：memory_id、scope、source（customer_stated / customer_confirmed / system_observed / model_inferred / staff）、verification、confidence、conditions、有效期、version、supersession、retention_basis、访问策略。

- 写管线：候选提取 → 验证门（影响资金/权益的事实必须显式确认；系统事实必须有回执）→ 去重合并 → 版本化替代 → 存储。禁止写入凭据、支付秘密、未验证的模型推断。
- 读管线：按作用域与目标过滤 → 新鲜度与条件检查 → 作为提示注入（不得覆盖当轮明示）→ 影响选择时写入决策理由；不可用时降级（现状保持）。
- 删除：客户可发起；覆盖主存储与任何派生摘要/缓存（当前无缓存，逐 tick 读取，保持）；墓碑与审计保留。
- 经验记忆使用规则：只在同类目标、同环境条件下作为候选提示，执行前必须重新验证环境前提，不得直接执行。

### 5.6 验证与闭环

- 完成条件由应用裁定（verify 回调）；证据必须新鲜、属于正确作用域、非模拟（现状保持）。
- 证据阶梯：系统回执 > 人工确认 > 客户确认；无系统回执的目标（如退款到账）以客户/人工确认 + 外部对账为证据，超时进 owner_review。
- 禁止：模型文本作为完成证据；mock 满足完成条件；未验证结果写入客户会话（现状保持，有测试覆盖）。
- 完成后：结果写入事件记忆，交付去重（现状保持）。

## 6. 收敛路线

细化切片与 PR 划分见 [agent-refactoring-plan.md](./agent-refactoring-plan.md) §4。

| 阶段 | 内容 | 验收门 |
|------|------|--------|
| P0 已完成 | 订单路径端到端（入口建任务→派发 worker→验证→回写）、偏好记忆、任务生命周期 | 现有集成测试（`tests/integration/test_chat_service_tasks.py`） |
| P1 受理层 | 目标受理抽取与泛化（intake）；订单路径迁移不回归 | 回归全绿；重发去重；FAQ 不误建任务 |
| P2 装配与域 | 策略解析注册表；订单域合并（domains/order） | 行为回归；第二 goal 冒烟测试 |
| P3 操作目录 | ticket.create / handoff.enqueue / notify.send 契约化；GOALS 开关 | 幂等重试不双执行；新旧路径等价 |
| P4 判断与环境 | 决策字段扩展；环境字段；≥2 个真实候选；健康驱动换路 | 环境场景测试：健康/库存/队列变化改变选择 |
| P5 记忆扩展 | 客户事实（验证门）+ 事件时间线 + 经验提示；读管线接入 | 删除覆盖派生；无秘密与未验证推断入库 |
| P6 写操作闭环 | 退款域 + 补偿 + 跨任务对象锁 + 费用/总时限/无进展预算 | unknown 写不双执行；预算耗尽进 owner_review |
| P7 旧管线收敛 | 冻结旧处理器为降级兜底；文档收敛 | 降级演练通过；文档无过时边界 |

每阶段的通用要求：集成测试先行、文档同步更新、不夸大声明（mock 与模拟证据不计入验收）。

## 7. 验收场景与断言

| 场景 | 期望 |
|------|------|
| 订单查询成功 | 1 次调用；证据归属匹配；会话仅 1 条回写 |
| 工具瞬时失败 | 退避重试后成功；重试键为 `request_key:retry`；账本记录两次尝试 |
| 工具永久失败 | 进 owner_review，不 resolve，不外泄 |
| mock 数据 | 不满足完成条件，不 resolve，不写入会话 |
| 主工具 health=degraded | 选择备选或询问客户；决策记录含拒绝理由 |
| 偏好过期 | 按默认值执行并记录降级标记 |
| 写操作超时 | 记 unknown 并对账；幂等键复用返回既有回执，不重复执行 |
| 客户取消（有未决操作） | 不再执行；未决操作转 owner_review |
| 多目标消息 | 主目标建任务；后续目标被记录且在依赖满足后执行 |
| 环境变化 | 事实过期后强制重新观察，不允许用旧证据完成 |
