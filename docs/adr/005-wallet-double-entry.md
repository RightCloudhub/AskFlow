# ADR 005：钱包采用复式分录、快照与独立哈希链

日期：2026-10-29。状态：Accepted defaults（用户 `keep going`）；财务上线口径待确认。相关：[数据模型](../mall/data-model.md)、[状态机](../mall/state-machines.md)。

## 决策

金额仅严格整数最小币种单位，DB BIGINT，API amount_cents，currency 明确。默认推荐 CNY，禁止 float/隐式跨币种。折扣/奖励按整数 basis points 计算，向下取整，残差归平台并在单据记录；不得用 Python round(float)。API 对 JS 安全整数边界设上限，超限财务导出用十进制字符串。

WalletService 是唯一记账写入口。wallet_journal_entries 每业务事件一条，wallet_postings 多条借/贷；应用写入前断言 sum(debit)=sum(credit)>0，并验证账户币种一致。数据库分录行要求金额正数、side 仅 debit/credit，journal 有已平衡摘要；跨行平衡通过事务校验和对账任务兜底，不能声称单行 CHECK 能保证跨行等式。

每账户指定 normal_side：资产/费用 debit，负债/收入 credit；快照余额 = normal_side 分录 − opposite_side 分录。用户钱包和冻结钱包是平台负债，禁止负数；平台清算账户可以按科目规则允许暂时负数。平台科目按 currency 唯一，不把所有账户当用户余额。

## 科目与示例

| 业务 | 借方 | 贷方 | 用户可用余额 |
|---|---|---|---|
| 第三方充值 10000 分 | 网关在途资产 10000 | 用户钱包负债 10000 | +10000 |
| 钱包支付 2500 分 | 用户钱包负债 2500 | 订单待结算负债 2500 | -2500 |
| 第三方订单支付 | 网关在途资产 | 订单待结算负债 | 不变 |
| 组合支付 | 用户钱包负债 + 网关在途资产 | 订单待结算负债 | 仅钱包部分减少 |
| 网关结算 | 平台现金资产 | 网关在途资产 | 不变 |
| 订单完成 | 订单待结算负债 | 销售收入 | 不变 |
| 退回钱包 | 订单待结算负债/退款清算 | 用户钱包负债 | +退款金额 |
| 原路网关退款 | 订单待结算负债/退款清算 | 网关在途/现金资产 | 不变 |
| 邀请奖励成熟 | 营销费用 | 用户钱包负债 | +奖励金额 |
| 冻结 | 用户钱包负债 | 用户冻结钱包负债 | 减可用、总额不变 |
| 解冻 | 用户冻结钱包负债 | 用户钱包负债 | 增可用、总额不变 |
| 手工更正 | 原分录对调冲正 + 新分录 | 两笔各自平衡 | 双人批准后变化 |

订单 PAID 不立即记收入，待完成才结转；已结转订单退款冲销售退回/退款清算，不能借不存在的待结算余额。优惠/物流/税额的独立科目扩展在正式财务口径确认后增加。

## 原子性与并发

1. 先以唯一 business_key 领取 journal 幂等；同 key 不同内容哈希返回 409，不能重用旧结果伪装新金额。
2. PG 按排序后的 account_id 锁定账户；SQLite BEGIN IMMEDIATE。统一跨资金流程锁顺序：订单/支付资源 → 财务链头 → 排序账户，防止互相反转造成死锁。
3. 更新财务链头 version CAS，得到递增链序号；哈希规范化包含 journal id、business_key、currency、全部排序分录、前哈希、操作者、UTC 时间与原分录引用。
4. 对用户账户条件更新 version 和 balance>=debit_delta；失败整体回滚，不重试到负数。允许受控重读重试整个事务，不能单独重试其中一条 posting。
5. 同事务追加 journal/postings、快照、审计、领域 outbox；flush/commit 失败则无资金生效。

Redis 锁/缓存只减少竞争，数据库唯一键、版本、非负 CHECK 与同事务分录决定正确性。缓存钱包余额不能作为扣款依据。链头每 currency 独立序列，不复用原 operation_ledger 的末条查询，避免并发分叉。

## 只追加与冲正

无 UPDATE/DELETE journal/posting API；ORM before_update/before_delete 拒绝，SQLite/PG 迁移添加阻止修改触发器，生产应用 DB 用户撤销 UPDATE/DELETE 权限。维护角色有独立凭据；篡改单行的测试使用专用测试绕过/维护通道，不能在正常 API 暴露关闭触发器。

每条冲正包含 reversal_of + 唯一引用，最多冲正一次；修复 journal 与审批单对应。对同一业务多次部分退款采用独立 refund_id key；总退款包括 pending/approved 的额度预留，不能只扣 settled 合计。

账户快照可以更新，但只有 WalletService 同事务 CAS；对账不能通过改快照掩盖分录篡改。若仅快照漂移、分录及哈希完整，可以经财务批准从分录重建快照并留审计；分录异常先冻结相关资金业务再调查。

## 支付、充值、退款的边界

支付单与订单分离。钱包扣款和组合支付的钱包预留先冻结，外部资金确认后完成 journal；外部失败/过期按唯一 key 解冻。第三方金额必须等于 server-computed external_amount_cents，币种/商户/业务标识也匹配。

mock 也 HMAC 验签、原始报文摘要/验签/处理状态持久化，channel_transaction_id 唯一；同流水号不同金额为冲突与风险事件，不能提前返回重复成功。支付单、订单状态、库存消耗、journal 和 outbox 在最终确认的同一事务完成。

真实外部退款先提交 Gateway INTENT 和 refund 单，再调用；mock 回执也经过同一确认/查证接口。回调丢失主动查询；未知结果禁止新退款键重放。退款按原支付拆分比例/钱包优先等明确策略分配，累计各通道退款不超过实收。

退款到账才能推进 REFUNDED/PARTIALLY_REFUNDED；申请/审批不能标记到账。超过限额必须权限审批，Gateway 与订单审批记录均保留。提现可选，推荐本期默认关闭，不暴露半成品提现端点。

## 邀请奖励和回收

推荐单层关系不可改、手机号验证、首个订单完成且过 7 天售后观察期后发奖；首单退款撤回 pending，已发奖通过冲正。用户已花光奖励时不允许把钱包扣负：生成奖励追偿负债/冻结待处理记录，挂人工审批，后续入账按明确政策抵扣；不能宣称总能立即现金撤回。

规则可配置，每日/累计奖励上限、设备/IP/手机号段/支付账户的哈希关联评分；手机号段/共享 NAT 只能作为风险线索，不单独永久封禁。奖励唯一键 relation+rule+source_order，规则版本在奖励上固化。

## 对账

每日（UTC 日期）和手工任务创建 reconciliation_runs，进行：每 journal 借贷平衡和摘要；每账户分录汇总与余额快照；链序连续/哈希完整；网关账单与 payments/refunds/topups 的金额/币种/状态/业务 ID 核对。

差异写 reconciliation_diffs，按 run+entity+kind 唯一；通知财务角色、暴露严重度/处置流程。hash mismatch、负余额、借贷不平衡为阻断型告警；普通网关在途时间差可延期重查。

双人调账：申请人需 wallet:adjust，审批人需 wallet:approve，二者不同、均短期 step-up、expected_version，审批一次。拒权同样写审计，不能在抛异常回滚后丢失拒权证据；拒权审计使用独立持久事务。

## 备选与后果

只有 balance+流水无法独立验证平衡，无法表达清算/冻结/营销费用，因此不选。直接复用 operation_ledger 存资金语义会混淆执行治理和账务，因此保留两套职责清晰的账，互相引用业务 ID。

链头和单用户账户是写热点，需要实际压测；不能以 Redis 锁掩盖吞吐瓶颈。复式记账不自动等于会计/监管合规，法定保留期、税务和科目口径需财务确认。M0 所有性能、安全与财务验收未执行。
